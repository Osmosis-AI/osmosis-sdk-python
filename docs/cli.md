# CLI internals (for contributors)

> The user-facing command + flag reference lives at [docs.osmosis.ai/cli/command-reference](https://docs.osmosis.ai/cli/command-reference). This page explains how the CLI is wired so you can add or change commands correctly.

## Entry point and registration

The console scripts `osmosis`, `osmosis-ai`, and `osmosis_ai` all map to `osmosis_ai.cli.main:main`. [../osmosis_ai/cli/main.py](../osmosis_ai/cli/main.py):

- `main()` calls `_register_commands()` once, then delegates to `run_cli(app, argv, prog_name=...)`. The program name is the invoked executable for the `osmosis-ai` and `osmosis_ai` aliases (so help and completion keep the alias) and `osmosis` otherwise. `run_cli` runs the command tree with `standalone_mode=False` so it can map exceptions to exit codes itself.
- Public commands are registered in `_add_commands()`, which both the module-level `app` (via `_register_commands()`) and `create_app()` use; add new public commands there, named from [../osmosis_ai/cli/command_registry.py](../osmosis_ai/cli/command_registry.py). It imports each command group **lazily inside the function**. Groups attach via `add_typer(...)`; the standalone `quickstart` / `doctor` / `upgrade` commands attach via `command(...)`. Two `rich_help_panel`s split the help: `Workflow Commands` (`quickstart`, `dataset`, `train`, `model`, `eval`, `benchmark`, `rollout`, `template`, `doctor`) and `Platform Commands` (`auth`, `secret`, `upgrade`).
- The root `_callback` resolves `--json` / `--plain`, builds an `OutputContext`, installs it on the Typer context, and registers `verify_output_emitted` on close. The CLI loads an explicit `--env-file` / `OSMOSIS_ENV_FILE`, or otherwise discovers the nearest `.env` from the working directory upward. Non-empty process variables take precedence, overlapping dotenv auth values must agree, and `--platform` overrides `OSMOSIS_PLATFORM_URL` for one invocation. Non-HTTPS non-loopback platform URLs are refused unless `OSMOSIS_ALLOW_INSECURE_PLATFORM_URL=1`. `hoist_format_selectors` lets the format flags appear anywhere on the line.

## Composing another CLI

`create_app(name=..., version_callback=..., upgrade_command=...)` in [../osmosis_ai/cli/main.py](../osmosis_ai/cli/main.py) registers the complete public command tree on a fresh Typer root, with independent nested registration metadata and shared handler functions. Downstream distributions can extend that root with `app.add_typer(...)` or `app.command(...)`, then call `run_cli(app, argv) -> int`. Creating or invoking another root does not register its commands on the public `osmosis` application. Do not modify the module-level `app` or copy its registration lists.

The SDK owns command handlers, root options, authentication, environment loading, workspace selection, output rendering, shell completion, and exit behavior. Downstream distributions explicitly replace the zero-argument version callback and Typer upgrade command when they have their own release channel; omitting either preserves SDK behavior. Structured error and warning envelopes always report the SDK version as `cli_version`, matching the `X-Osmosis-CLI-Version` request header, and SDK remediation hints (for example `osmosis auth login`) name the `osmosis` executable. `run_cli` uses the app's name for help and completion unless an entry point supplies `prog_name` for a console alias, rejects duplicate command and group names recursively before invoking a handler, and resolves structured error paths against the composed command tree. Keep heavy imports inside handlers and retain a bare-version fast path in the composing entry point if needed.

## Workspace scope

Workspace-scoped platform commands normally derive `X-Osmosis-Git` from the current Osmosis workspace directory. A root `--workspace <name>` selection instead sends only `X-Osmosis-Workspace` and skips local Git and scaffold discovery; the selection is per invocation and is not persisted. This applies to benchmark catalog/run commands and submit, dataset/model/secret commands, and train/eval list, info, logs, retry, and stop. Structured output records `workspace.name` for an explicit selection and does not fabricate `git` or `workspace_directory` fields.

Train and eval submit remain source-backed. With `--workspace`, their config argument must be absolute; the CLI locates the containing Osmosis Git workspace, checks the selected workspace's connected repository against that Git identity, and submits with only `X-Osmosis-Workspace`. The local Git identity is retained in structured output because it is real source context, not inferred platform state. Without `--workspace`, their existing current-directory behavior is unchanged.

Submit confirmations put the target first in both human-readable output and `--json` `INTERACTIVE_REQUIRED.details.summary`. Train and eval always show their source `Repository`; an explicit `--workspace` adds a leading `Workspace` row. Without an explicit workspace, the run goes to the workspace connected to that repository. Benchmark submit shows only `Workspace` with an explicit selection, or only `Repository` for the current-directory Git scope otherwise. For benchmark submits, `Repository` identifies the connected workspace that receives the run, not benchmark source code.

## Authentication storage and environments

`OSMOSIS_TOKEN` is the highest-priority implicit authentication source and is intended for CI/CD, agents, and other non-interactive processes; an explicit `auth login --token` overrides it and persists the supplied token. Set `OSMOSIS_TOKEN_PLATFORM_URL` to the same normalized origin as `OSMOSIS_PLATFORM_URL`; this binding is required whenever the active platform is not the default platform and recommended in all environments. For backward compatibility, an unbound environment token is accepted only for the default platform URL. Interactive/device login and `auth login --token` persist credentials in the operating-system keyring; the JSON file under `~/.config/osmosis/` then contains only non-secret metadata. Existing file-backed tokens remain readable for migration.

Hosts with no reachable keyring (headless containers, remote shells, sandboxes) would otherwise be unable to complete a login, so the token falls back to `~/.config/osmosis/credentials.json`, written atomically with owner-only permissions (`0600` in a `0700` directory), and the login prints a `KEYRING_UNAVAILABLE` warning. A previous keyring-backed login that cannot be read on such a host is left in place and reported as not revoked. `OSMOSIS_TOKEN_STORE` pins that choice: `keyring` restores the strict behavior and fails the login before a token is minted when no keyring is available, `file` skips the keyring entirely, and the default `auto` prefers the keyring. `auth whoami` reports which backend holds the active token.

Persistent credentials are keyed by the normalized platform URL, so credentials for multiple platform environments can coexist without overwriting one another. Read-only commands preserve and reject corrupt or unknown shared metadata; explicit login/logout recover by moving it to a non-overwriting `credentials.json.bak[.N]` backup. Logout removes local metadata even when the current host cannot access the system keyring and emits a cleanup warning. An HTTP 401 reports an expired or revoked session but never deletes local credentials; only explicit `auth logout` changes stored state. `auth whoami` reports both the effective source and whether a persistent login also exists, while logout makes it explicit when `OSMOSIS_TOKEN` remains active.

The nearest `.env` is loaded automatically, so a workspace can set only `OSMOSIS_PLATFORM_URL` and select its platform-scoped keyring login without exporting it in every shell. Use `--env-file` / `OSMOSIS_ENV_FILE` to select another file explicitly; non-empty process variables still win, and `--platform` has the final override. If a dotenv file contains `OSMOSIS_TOKEN`, that token intentionally takes precedence over the keyring for the process, so keep `OSMOSIS_TOKEN`, `OSMOSIS_PLATFORM_URL`, and `OSMOSIS_TOKEN_PLATFORM_URL` together. Profiles already loaded by `uv` are accepted when overlapping values agree; missing values are filled from dotenv instead of being treated as a conflict.

## Command shells delegate; they don't do work

Files in [../osmosis_ai/cli/commands/](../osmosis_ai/cli/commands/) are thin Typer shells. Each command parses options and delegates to business logic:

- platform-facing logic lives in [../osmosis_ai/platform/cli/](../osmosis_ai/platform/cli/) (e.g. `dataset.py`, `train.py`, `eval.py`, `secret.py`);
- eval/rubric logic lives in [../osmosis_ai/eval/](../osmosis_ai/eval/).

Module-level imports in `commands/` are kept light: `typer`, `cli.errors`, the lightweight `osmosis_ai.platform.constants` (pagination limits), and stdlib. Everything heavy (`rollout.*`, `platform.api.*`, `platform.cli.*`, `eval.*`, `cli.console`) must be imported **inside the function** to keep CLI startup fast — see the lazy-loading section of [architecture.md](./architecture.md).

`osmosis benchmark` puts the benchmark first, mirroring the platform's
Benchmarks pages: top-level `list` and `info` act on benchmarks (the workspace
list and one benchmark's page - `info` shows its metadata, leaderboard, and
runs), `submit` starts a run, and run lifecycle lives under the nested
`benchmark runs list|info|logs|stop|download` namespace.

List output includes a shell-safe benchmark `Key`, such as
`terminal-bench-2-1`. Pass that key to `osmosis benchmark info <key>`;
exact display names and UUIDs remain supported for compatibility.

## Commands return results; they don't print

The Typer app is created with `result_callback=render_command_result` ([../osmosis_ai/cli/main.py](../osmosis_ai/cli/main.py)). A command function **returns** a `CommandResult`; the callback renders it in the active format. Do not `print()` from a command — return a typed result instead.

Result types ([../osmosis_ai/cli/output/result.py](../osmosis_ai/cli/output/result.py)):

| Type | Use |
|------|-----|
| `ListResult` | A single list/table |
| `SectionedListResult` | Multiple named lists (e.g. base + LoRA models) |
| `DetailResult` | One resource's fields/sections |
| `OperationResult` | A mutation's outcome |

Serializers that turn API models into these shapes live in [../osmosis_ai/cli/output/serializers.py](../osmosis_ai/cli/output/serializers.py).

## Output envelopes

[../osmosis_ai/cli/output/renderer.py](../osmosis_ai/cli/output/renderer.py) builds the machine contract. Every JSON success envelope carries `schema_version: 1` and a shape matching the result type (`_envelope_list`, `_envelope_sectioned_list`, `_envelope_detail`, `_envelope_operation`). Rich is the default for humans; `--plain` is intentionally low-noise text (not a strict schema).

The output context, format enum, and selector resolution live in [../osmosis_ai/cli/output/context.py](../osmosis_ai/cli/output/context.py); the full output surface is re-exported from [../osmosis_ai/cli/output/__init__.py](../osmosis_ai/cli/output/__init__.py). Serializer names are lazy (PEP 562) so importing the package does not load platform API models.

## Errors

Raise `CLIError` ([../osmosis_ai/cli/errors.py](../osmosis_ai/cli/errors.py)) — the single error type shared by every domain. `CLIError.code` is a `CLIErrorCode` `StrEnum`. `run_cli` funnels all exceptions through `_handle_cli_error`:

- in JSON mode, `classify_error()` + `emit_structured_error_to_stderr()` write a structured error envelope (with a CLI error `code`, command path, and SDK version) to **stderr** ([../osmosis_ai/cli/output/error.py](../osmosis_ai/cli/output/error.py));
- otherwise a plain `Error: …` line is printed.

Under `run_cli`, the envelope's command path is resolved from the actual composed command tree, so nested extensions and unknown subcommands are retained even when root option parsing fails. Root options with values are skipped, including `--workspace value` and `--workspace=value`. Direct callers of `command_path_for_error` without a root command get the Click context's subcommand path, or `<root>` when there is none. Helpers therefore raise `CLIError` instead of writing envelopes themselves; for example, `require_confirmation` raises `INTERACTIVE_REQUIRED` with the prompt and its context in `details`.

Not-logged-in failures use `AUTH_REQUIRED`. `SubscriptionRequiredError` maps to `SUBSCRIPTION_REQUIRED` or `BILLING_REQUIRED` from the platform `error_code`; a generic HTTP 403 stays `PLATFORM_ERROR`. The error object has `code`, `message`, and `details` only — `request_id` is omitted because the platform client does not expose one.

Platform API and login errors share one error-body reader and prefer a non-empty string `message` over the legacy `error` field, falling back to a non-empty string `error` when no usable explanation is supplied. Authentication and repository-scope guidance, validation issue details, and device-login polling decisions remain unchanged. A server-supplied login `message` is surfaced verbatim as the explanation, prefixed with the operation context and suffixed with the HTTP status; a bare error code is paired with the status-specific text. Login HTTP errors use the same status classification as API errors (`VALIDATION`, `CONFLICT`, `RATE_LIMITED`, and so on), except that a login-endpoint 404 stays `PLATFORM_ERROR` because it signals a wrong platform URL rather than a missing resource. Every login error, including `AUTH_REQUIRED`, retains `status_code` and any platform code in JSON details; every login HTTP error, including a verification 401 and a terminal device-poll error, also retains the parsed response body, layered like API error details (platform code, then the response body, then `status_code`). Connection failures and timeouts share one wording across the API and login paths: both a connect-phase timeout (which urllib wraps in `URLError`) and a response-read timeout produce retry guidance, and a single timed-out device-login poll is retried until the login deadline instead of aborting the flow. A non-object JSON body or malformed `expires_at` on a successful login response is reported as an invalid platform response rather than `INTERNAL`.

HTTP 409 responses whose `error` (or `code`) is `deployment_conflict` remain `CONFLICT` errors on both the API and login paths. A usable server `message` is surfaced; a missing or invalid message, or one that mentions reloading (the edge router's browser-only prompt, whose exact wording is not stable), is replaced with CLI guidance to retry shortly and contact support if the conflict persists. The JSON error details retain the original response, HTTP status, and platform code. Conflicting requests are not automatically retried.

JSON success and error envelopes are encoded with `allow_nan=False`. Non-finite metric values are sanitized to `null` in train/eval metrics exports (including the file written by `train info --output`); any remaining non-finite float fails the command rather than emitting invalid JSON. `train info --output` keeps an existing file unless `--overwrite` is passed, reporting `save_warning` instead (also when another process creates the file mid-export), and writes through a temporary file that is flushed and synced before being atomically linked, or with `--overwrite` replaced, into place. For an explicit output path without `--overwrite`, publication requires filesystem hard-link support; if unavailable, no export is published and `train info` still succeeds with `save_warning`. The default `.osmosis/metrics/` export is the CLI's own copy and is refreshed in place. Existing-file warnings retain the requested output path rather than its resolved absolute or symlink target path.

Unknown exceptions become `INTERNAL` with a generic message. Set `OSMOSIS_DEBUG=1` to append the original exception and traceback to stderr (the JSON envelope is unchanged). Every printed error, including that trace, passes the [invocation error boundary](#known-secret-output-boundaries).

`KeyboardInterrupt` / `click.Abort` exit `130`; `typer.Exit` / `SystemExit` preserve their code.

## Known-secret output boundaries

[The shared redactor](../osmosis_ai/_redaction.py) protects known plaintext values at presentation boundaries. The secret-set, train/eval/benchmark submit, and eval-retry methods in [the API client](../osmosis_ai/platform/api/client.py) pass supplied values to `platform_request(secret_values=...)`. The [transport](../osmosis_ai/platform/auth/platform_client.py) classifies protocol errors from the body as received, then builds messages, issues, and details only from a copy decoded after known values were replaced in the received text, because decoding first could split a JSON-shaped credential across fields or unescape it into another spelling; a body that the replacement leaves unparseable yields no details. Version warnings are sanitized the same way. Sensitive requests omit opaque response-body fallbacks and suppress raw exception chains, preventing JSON escaping or truncation from bypassing matching. Calls without supplied values keep their existing diagnostics.

Successful API responses retain their field names and are validated against their result model types before SDK use or presentation. Malformed responses produce a generic platform error without exposing parser inputs or raw exception chains. Command results keep that protocol data; the [renderer](../osmosis_ai/cli/output/renderer.py) scrubs the invocation's known values (below) from what it prints. JSON output is scrubbed value by value while envelope keys, `schema_version`/`status`/`operation`, and the field names of the records directly under the envelope keep their form; plain and rich output are checked as finally written, after plain normalization (tabs and newlines become spaces) and rich bracket unescaping, which could otherwise rebuild a value that no field held. Do not apply a generic redactor to protocol data before parsing it, or register a secret-bearing endpoint without forwarding its secret context to the transport and registering it with the invocation.

Nested diagnostic JSON includes keys, strings, numbers, booleans, and nulls. A matching scalar becomes a redaction marker; unrelated scalar types are preserved. Matching is deterministic across secret order and overlap, and checks that replacement markers cannot recreate a secret. Each known value is matched in these spellings: the literal value; its whitespace-trimmed form, because secret loaders, HTTP header parsing, and child processes commonly strip surrounding whitespace before use or logging; each line of a multiline credential that contains a letter or digit, also trimmed, for line-oriented logs; the JSON string escapes of all of these, with and without ASCII escaping, so a JSON body embedded in text cannot hide one; and their Python `repr` bodies in either quote style, because SDK messages, container text, and parser errors quote values with `repr`, which escapes quotes, backslashes, and unprintable characters (such as `\x07`) differently from JSON. Text containing JSON escapes is also checked after decoding them once, with UTF-16 surrogate pairs such as `\uD83D\uDD11` combined into one character as JSON defines; when any escape, standard or not (such as `\u0073` for an ASCII letter, or `\/`), spells a known value, the whole string becomes a marker, because a reader can decode it. Formatting-only lines such as `{`, `]`, or blanks are skipped because they carry no secret and would match unrelated output; line-oriented scrubbing still checks the rejoined text for a complete multiline value, so one made only of such lines is redacted while unrelated lines survive. Structured data nested more than 100 levels deep keeps its outer shape with a marker in place of the deeper branch. Other transformations are not matched: case changes, provider masking such as `sk-****abcd`, truncated prefixes, URL or base64 encoding, JSON encoded more than once, and a JSON-shaped credential that an upstream re-serializes or takes fields from. Short values can suppress diagnostic context or replace a normally numeric presentation value with a string; protocol parsing, status classification, and business decisions must occur first. Envelope keys, top-level presentation field names, and CLI status codes are protocol identifiers, not secret echoes; nested mapping keys are sanitized with their values.

Local eval uses the same implementation for child output before trimming, structured log details before encoding, terminal diagnostic callbacks, model preflight failures, journal error labels, and provider error responses before encoding or truncation. The runner knows the ambient provider and platform keys before it reads any run state. Replayed journal records keep their bytes on disk, but the index, summary, and failure rows built from them are scrubbed with the values known now, so a diagnostic recorded before a key was known does not reach new output. The LLM bridge receives every registered run secret when it is created and replaces known values in a provider error's text before decoding, re-encoding, normalizing, or truncating it; a body that parses is also checked value by value, and one that does not (plain, malformed, truncated, or nested too deeply) stays as that scrubbed text. A successful provider response is converted and serialized inside the same handler, so a malformed field whose error quotes it becomes a sanitized bridge error rather than a web-server traceback. The bridge error text is made UTF-8 encodable (a lone surrogate becomes its `\udXXX` escape) before it is returned or logged, because a response encoder or log handler failing on it would report the provider error being handled, chain included. For programmatic callers, [`LocalEvalRunner.run`](../osmosis_ai/eval/local/runner.py) scrubs the runner's own errors (`LocalEvalError`, `LocalEvalStateError`) as complete messages and drops their exception chain; other exceptions, including any raised by an `after_finalize` callback, pass through unchanged. See [local eval secrets](eval-run-local.md#secrets). This is protection for known values in the spellings above, not a decoder for arbitrary transformations in third-party output or a scrubber for user-authored datasets, trajectories, and artifacts.

Each [`run_cli`](../osmosis_ai/cli/main.py) invocation collects known values through `register_invocation_secrets` in [the shared redactor](../osmosis_ai/_redaction.py): the root callback registers the ambient provider and platform keys of the final environment (after `--env-file`; values of at least 8 characters, the list the runner uses) before any command runs, and commands add run secrets resolved from `--secrets-file`, the environment, or a prompt, and the value read by `secret set`. Every command's output uses them: success output through the renderer, warnings in every format, and rich text, errors, and warnings as Rich will render them, after markup and its escapes. Every error the CLI prints is scrubbed with them: the JSON envelope's message and details, the plain or rich message (including the raw message of an unexpected exception or an `eval run --upload` failure), and the `OSMOSIS_DEBUG` trace with its exception chain, whose stack is kept while each line is scrubbed. Messages are scrubbed line by line, so a line that cannot be made safe becomes a marker while the rest, such as a retry command, stays; details are scrubbed value by value: keys and numbers that match no known value keep their form and type, while a matching key or number becomes a marker. Classification happens before this boundary, and exception objects raised to Python callers keep their original text; the boundary governs what the CLI prints. If reporting an error itself fails, the CLI prints a fixed `INTERNAL` message instead of raising, because that failure would carry the original error and its chain past every scrub; a secret-bearing transport request likewise turns a failure while translating an HTTP error into a generic `API error: HTTP <status>.` without its chain. A command that obtains a secret value any other way must register it. Prebuilt Rich renderables such as tables and panels that a command passes to the console are SDK-authored and not re-scanned.

## Conventions when adding a command

1. Put the Typer shell in `cli/commands/`; put the logic in `platform/cli/` or `eval/`.
2. Keep module-level imports minimal; lazy-import heavy deps inside the function.
3. Return a `CommandResult`; never print directly. Annotate handlers as `-> CommandResult`. Reuse [../osmosis_ai/cli/options.py](../osmosis_ai/cli/options.py) for `--limit` / `--all` / `--cursor`.
4. Raise `CLIError` for user-facing failures.
5. Support non-interactive flows (`--yes`, `--token`, `--env`) so `--json` / `--plain` don't dead-end on a prompt (`INTERACTIVE_REQUIRED`).
